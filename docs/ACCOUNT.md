# Account data controls

Website users can open `/account`, download a JSON export, and type the exact text `DELETE` to permanently delete their ContextSpeak account. Account controls require a website cookie session; paired extension bearer credentials cannot invoke them. Existing global origin/CSRF checks apply to deletion. Export requests also send the tab's CSRF token, preventing a stale tab from exporting a different account after its cookie changes.

## Export

`GET /v1/account/export` returns `contextspeak-data.json`, schema version 1. It contains account collection/translation/learning preferences, learning items, lookups, review cards/events, practice attempts, game attempts/levels, and generated-speech metadata. Every query scopes ownership by the authenticated user ID. Login attempts, session credentials, pairing proofs, internal payload hashes, and audio bytes are excluded. Legacy raw-media fields in JSON payloads are removed. Exported text and source addresses may still be sensitive.

The service uses one repeatable-read transaction and keyset pages of 100 rows. It opens a private temporary file, immediately unlinks its directory entry, and writes a complete JSON snapshot through the retained file descriptor before sending the attachment. There is no record-count cap or silent truncation. The database snapshot has a 120-second timeout; storage or timeout failures fail the request before the attachment is sent. The descriptor closes in a `finally` block after delivery or error; the operating system also releases the already-unlinked file if the process crashes. Production should still use an encrypted/private temporary volume. A filesystem that cannot unlink an open file fails the export before writing account data. The download itself belongs to the user; deletion does not remove downloaded copies from their device. Export requests have a small per-process rate limit; production should also enforce shared edge limits and adequate temporary disk capacity.

## Deletion and cleanup

`POST /v1/account/delete` accepts `{ "confirmation": "DELETE" }`. The service locks the owner's `User` row, inserts a standalone `AccountDeletion` tombstone, and deletes the user in one database transaction. Foreign-key cascades remove learning records, settings/profile, sessions, owned pairings, game history, and speech metadata. It clears the website cookie; all website and extension credentials become unusable. Server-created OIDC identities pin the authenticated user UUID through a private WeakMap; a stale in-flight request cannot upsert a new account after deletion. Provider results that commit through the same owner lock and existing foreign keys cannot recreate records for that deleted UUID. The shared deletion callback purges owner-scoped translation, speech, and expansion caches. Cache retention also verifies a live owner under a database row lock, so late provider results cannot recreate a deleted owner’s cache entries. Pending cache generations carry per-work identity rather than an indefinitely growing set of deleted IDs. Signing in later can intentionally create a fresh account with a new UUID.

The tombstone has no foreign key to the deleted user. It retains only the account UUID, deletion time, whether speech assets existed, and cleanup progress/attempt timestamps. Retain this minimal deletion ledger until the corresponding recoverable backups have expired; do not cascade or purge it with user data.

After the database commits, the service invokes the shared `SpeechStore.cleanup()` instance. That store serializes with audio writes and removes files whose indexed owner/asset was deleted. A cleanup/storage failure returns `{ "deleted": true, "cleanupPending": true }`; it never reports that the account still exists. The tombstone remains pending for automatic retry on startup and every 60 seconds, in batches of at most 100 records. Successful cleanup marks `cleanupCompletedAt`; retries are idempotent. Without a configured store, a tombstone that had indexed speech assets stays pending. An account with no indexed assets can complete without a store. Keep the same storage directory available after restart. If multiple replicas or storage directories can hold private audio, deployment must supply a shared store or coordinate completion across every copy; a single process cannot attest to remote disks. Monitor pending tombstones and repeated cleanup attempts.

## Backup recovery

Database deletion cannot rewrite existing backups. Before restoring traffic, fetch the latest deletion ledger from outside the restored backup's rollback horizon. Replay every tombstone against its matching `User.id`, deleting matching restored users with database cascades. Preserve the UUID and `hadSpeechAssets`, insert/upsert the tombstones into the restored database, and reset their `cleanupCompletedAt` to null. Run `new AccountService(prisma, sharedSpeechStore).retryCleanup()` until no applicable pending tombstones remain, and verify the restored private audio store. The method returns no completion proof: inspect `cleanupCompletedAt` and pending counts. It processes at most 100 tombstones per invocation. Do not expose a recovered database or audio store before replay and cleanup verification. A stale backup of the ledger alone is insufficient. Backups need a documented retention/expiry policy and the independent ledger needs matching access controls. A fresh account UUID created after deletion must not be deleted by an older UUID's tombstone.

These controls implement active database deletion and local storage cleanup. They are not deployment evidence, an empirical privacy audit, or a promise about third-party AI provider retention. Operators must separately document provider data handling, backup retention, logs, temporary storage, and all storage replicas.
